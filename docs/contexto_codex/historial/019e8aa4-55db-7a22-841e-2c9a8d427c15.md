1. Toma dos audios: una **referencia** y una grabación de **usuario**.
2. Usa **Demucs** para separar la voz del resto de la música.

4. Guarda los datos en CSV (`ref.csv`, `usr.csv`) con tiempo, frecuencia y nota estimada.
5. Compara las curvas de afinación usando **DTW** para alinear ambas interpretaciones aunque no estén exactamente sincronizadas.
6. Devuelve métricas como:
   - `error_prom`: error promedio absoluto en cents.
   - `desviacion`: variabilidad del error.
   - `tendencia`: si el usuario tiende a cantar más `agudo` o más `grave`.

## Codex (final_answer)

Sí. Para dar ese siguiente paso, yo separaría los requisitos en módulos claros:

**Requisitos Funcionales**

1. **Gestión de canciones**
   - Permitir registrar varias canciones disponibles para karaoke.
   - Cada canción debe tener al menos:
     - nombre
     - artista
     - archivo de audio original
     - pista vocal de referencia
     - pista instrumental
     - datos de pitch de referencia
   - Permitir seleccionar una canción desde una interfaz.
   - Permitir agregar nuevas canciones al sistema.
   - Permitir eliminar o actualizar canciones existentes.

2. **Preprocesamiento de canciones**
   - Separar automáticamente la canción en voz e instrumental usando Demucs.
   - Guardar la pista vocal separada.
   - Guardar la pista instrumental o acompañamiento.
   - Extraer el pitch de la voz de referencia.
   - Guardar el pitch de referencia para evitar recalcularlo cada vez.

3. **Interfaz de usuario**
   - Mostrar una lista de canciones disponibles.
   - Permitir seleccionar una canción.
   - Mostrar información básica de la canción seleccionada.
   - Tener botones para:
     - reproducir instrumental
     - iniciar grabación
     - detener grabación
     - comparar interpretación
   - Mostrar resultados de afinación después de cantar.

4. **Reproducción instrumental**
   - Reproducir la pista instrumental de la canción seleccionada.
   - Permitir que el usuario cante encima mientras suena.
   - Sincronizar el inicio de la reproducción con la grabación del micrófono.
   - Permitir detener la reproducción y grabación.

5. **Captura de voz del usuario**
   - Detectar el micrófono del ordenador.
   - Grabar la voz del usuario mientras canta.
   - Guardar la grabación del usuario como archivo WAV.
   - Idealmente reducir ruido o evitar que la instrumental se filtre demasiado en el micrófono.

6. **Comparación de afinación**
   - Extraer pitch de la grabación del usuario.
   - Comparar el pitch del usuario con el pitch de referencia de la canción seleccionada.
   - Usar alineamiento temporal, como DTW, para tolerar pequeñas diferencias de timing.
   - Calcular métricas como:
     - error promedio en cents
     - desviación
     - tendencia a cantar más agudo o grave
     - porcentaje aproximado de afinación correcta

7. **Visualización de resultados**
   - Mostrar un resumen numérico del desempeño.
   - Mostrar si el usuario cantó más agudo o más grave.
   - Mostrar una gráfica comparando la curva de pitch de referencia con la del usuario.
   - Opcionalmente mostrar resultados por secciones de la canción.

**Requisitos Técnicos**

1. **Almacenamiento**
   - Crear una carpeta o base de datos para canciones.
   - Guardar metadatos en JSON, CSV o SQLite.
   - Mantener rutas ordenadas para:
     - audio original
     - vocal de referencia
     - instrumental
     - pitch de referencia
     - grabaciones del usuario

2. **Estructura sugerida**
   ```text
   canciones/
     cancion_id/
       original.wav
       vocals.wav
       instrumental.wav
       ref_pitch.csv
       metadata.json

   grabaciones/
     cancion_id/
       usuario_fecha.wav
       resultado_fecha.json
   ```

3. **Librerías probables**
   - `demucs` para separar voz/instrumental.
   - `librosa` para cargar audio.
   - `pyworld` para extraer pitch.
   - `dtw` para comparación.
   - `sounddevice` o `pyaudio` para grabar micrófono.
   - `soundfile` para guardar WAV.
   - `pygame`, `sounddevice` o `playsound` para reproducir instrumental.
   - `tkinter`, `streamlit`, `customtkinter` o una app web para la interfaz.

4. **Sincronización**
   - La grabación del usuario debe empezar al mismo tiempo que la reproducción instrumental.
   - Se debe registrar duración, inicio y fin de la toma.
   - El sistema debe cortar o alinear la grabación según la duración de la canción.

5. **Compatibilidad**
   - Debe funcionar en Windows.
   - Debe reconocer micrófonos disponibles.
   - Debe manejar archivos `.wav`, idealmente también `.mp3`.

**Requisitos No Funcionales**

1. **Usabilidad**
   - La interfaz debe ser simple: elegir canción, presionar cantar, ver resultado.
   - No debe requerir comandos manuales para cada canción.
   - Debe mostrar mensajes claros mientras procesa.

2. **Rendimiento**
   - El preprocesamiento con Demucs puede ser lento, pero debe hacerse solo una vez por canción.
   - La comparación debe ser relativamente rápida después de cantar.
   - El pitch de referencia debe quedar cacheado.

3. **Robustez**
   - Manejar errores si falta un archivo.
   - Manejar canciones sin voz clara.
   - Manejar grabaciones silenciosas o con poco volumen.
   - Evitar comparar si no se detectó pitch suficiente.

4. **Calidad de audio**
   - Recomendar audífonos para evitar que la instrumental entre al micrófono.
   - Ajustar nivel de entrada del micrófono.
   - Posiblemente aplicar filtros simples o detección de voz.

5. **Escalabilidad**
   - El sistema debería permitir agregar muchas canciones sin cambiar código.
   - Las canciones deberían cargarse desde metadatos, no estar escritas manualmente en `main.py`.

**Requisitos Para Una Primera Versión MVP**

Para avanzar sin hacerlo demasiado grande de golpe, el MVP podría ser:

1. Registrar canciones desde archivos `.wav`.
2. Separar voz/instrumental con Demucs.
3. Guardar metadatos en JSON.
4. Mostrar canciones en una interfaz simple.
5. Seleccionar canción.
6. Reproducir instrumental.
7. Grabar micrófono al mismo tiempo.
8. Extraer pitch del usuario.
9. Comparar contra pitch de referencia.
10. Mostrar resultado numérico y gráfico.

Ese sería el siguiente paso lógico: pasar de un script fijo con `referencia.wav` y `usuario.wav` a una aplicación donde cada canción queda preparada, seleccionable y reutilizable.

## Codex (final_answer)

Sí, esto ya es un problema más de **calidad de señal + criterio de detección**, no solo de interfaz.

Yo lo abordaría en capas:

1. **Separar el problema**
   Hacer tres pruebas cortas:
   - Micrófono en silencio total.
   - Instrumental sonando, pero tú sin cantar.
   - Tú cantando con audífonos, sin que la instrumental salga por parlantes.

   Si en la segunda prueba aparecen notas, el micrófono está captando la instrumental y el detector la interpreta como voz. Eso explicaría muchos falsos positivos.

2. **Usar audífonos como prueba base**
   Para medir afinación, lo ideal es que el micrófono reciba casi solo voz. Si la instrumental sale por parlantes, el algoritmo puede detectar guitarra, piano, bajo, armónicos o reverberación como si fueran canto.

3. **Agregar calibración de ruido**
   Antes de cantar, pedir 2 o 3 segundos de “silencio” para medir el ruido ambiente. Luego se ignoran notas cuya energía esté cerca de ese ruido base. Esto sería mejor que usar un umbral fijo.

4. **No aceptar cualquier pitch**
   Ahora probablemente se acepta una nota apenas aparece. Conviene exigir:
   - duración mínima, por ejemplo 80-150 ms;
   - energía suficiente;
   - estabilidad mínima;
   - rechazo de saltos imposibles, por ejemplo cambios de más de una octava en muy poco tiempo.

5. **Mostrar confianza**
   No todo pitch detectado debería valer igual. La interfaz podría diferenciar:
   - nota segura;
   - nota dudosa;
   - silencio/no voz.

   Así evitaríamos que una detección accidental tenga el mismo peso visual que una nota cantada estable.

6. **Filtro distinto para tiempo real y resultado final**
   En vivo se necesita baja latencia, pero eso lo hace más sensible a errores. El resultado final puede usar un filtro más fuerte porque ya no importa la latencia. Es normal que la curva en vivo sea más “nerviosa” y la final más limpia.

7. **Probar otro detector**
   `pyworld` puede ser rápido, pero en ruido o instrumentos puede inventar saltos. Podríamos comparar con `librosa.pyin`, `CREPE/torchcrepe` o `praat-parselmouth`. Para tesis sería muy bueno justificar cuál funciona mejor con tus grabaciones.

Mi recomendación concreta: antes de seguir ajustando filtros a ciegas, hagamos un **modo diagnóstico de detección**: que muestre/guarde voz grabada, energía, pitch crudo, pitch filtrado y segmentos descartados. Así sabremos si el problema viene de ruido ambiental, instrumental entrando al micrófono, umbral bajo, saltos del algoritmo o exceso de sensibilidad en silencios.

```text
canciones/

grabaciones/
  fdsofdisj_9425509d/
```

**Implicación simple y recomendada**

Editar canción debería actualizar solo:

```json
{
  "titulo": "Nuevo titulo",
  "artista": "Nuevo artista"
}
```

en:

```text
canciones/<song_id>/metadata.json
```

Ventajas:

- No se mueven archivos.
- No se rompen rutas a `original`, `vocals`, `instrumental` ni `ref_pitch.csv`.
- No se pierden grabaciones.
- No hay que reprocesar la canción.
- Las tomas siguen asociadas por `song_id`.
- Es rápido y seguro.

**Detalle importante con las tomas**

Actualmente cada toma guarda también una copia del nombre/artista:

```json
"song_title": "...",
"artist": "..."
```

Entonces habría que decidir:

1. **No actualizar tomas antiguas**  
   Las tomas conservan el nombre que tenía la canción cuando se grabaron. Esto sirve como “histórico”.

2. **Actualizar también las tomas**  
   Cuando cambias título/artista, se recorren los archivos:

```text
grabaciones/<song_id>/*_toma.json
```

y se actualizan `song_title` y `artist`.

**Lo que evitaría**

No renombraría la carpeta ni el archivo de audio:

```text

```

Aunque el nombre quede “feo” internamente, es mejor. Si intentamos renombrar carpetas/archivos, habría que actualizar muchas rutas guardadas en JSON, revisar salidas de Demucs, grabaciones, referencias y posibles rutas absolutas/relativas. Mucho riesgo para un cambio que es solo visual.

Yo vería estas opciones:

**Opción 1: Referencia en bloques, usuario en línea**
Es la más parecida a la imagen.

- **Referencia**: bloques horizontales naranjos por cada nota esperada.
- **Usuario**: línea blanca encima, siguiendo la afinación real detectada.
- **Silencios**: espacios vacíos, sin líneas conectando una nota con otra.
- **Cursor**: línea vertical que avanza con la canción.
- **Eje Y**: notas tipo `Do3`, `Re3`, `Mi3`, etc.

Esta sería mi recomendación para la vista **Practicar**, porque el usuario entiende rápido: “debo cantar dentro del bloque”.

**Opción 2: Referencia como zona de tolerancia**
Parecida a la anterior, pero más útil para evaluación.

- **Referencia**: banda horizontal semitransparente, por ejemplo ±50 cents.
- **Centro de la nota**: línea fina dentro del bloque.
- **Usuario**: línea blanca o celeste.
- Si la voz cae dentro de la banda, se ve correcto.
- Si sale, queda visualmente claro cuánto se alejó.

Esta opción es buena porque no obliga a que la voz sea una línea perfecta. Para canto real es más natural.

**Opción 3: Usuario coloreado por precisión**
Mantiene bloques de referencia, pero la línea del usuario cambia de color.

- Verde: dentro de margen aceptable.
- Amarillo: cerca, pero algo desviada.
- Rojo: bastante fuera.
- Gris/transparente: baja confianza o ruido.

Visualmente sería muy claro para resultados, aunque durante el canto podría distraer un poco si cambia demasiado.

**Opción 4: Dos capas separadas**
En vez de poner todo encima:

- Arriba: referencia esperada como bloques.
- Abajo: voz del usuario como bloques o línea.
- Mismo eje temporal.
- Misma grilla de notas.

Esta opción sirve mucho para **Resultado** o **Detalle**, porque evita que referencia y usuario se tapen entre sí. Es menos “karaoke en vivo”, pero más analítica.

**Opción 5: Bloques vs bloques**
En lugar de mostrar al usuario como línea continua:

- **Referencia**: bloques naranjos.
- **Usuario**: bloques generados desde la nota detectada estable.
- Cada bloque del usuario se colorea según cercanía.

Esto se vería más limpio que una línea temblorosa, pero perderías información fina de vibrato, inestabilidad y transiciones.

Mi propuesta sería combinar:

- **Practicar**: opción 1 o 2. Referencia en bloques, usuario en línea blanca, cursor vertical.
- **Resultado**: opción 3. Misma gráfica, pero con color según precisión.
- **Detalle**: opción 4. Referencia y usuario separados, con zoom y scroll.
- **Historial**: miniaturas tipo opción 5, más limpias.

## Codex (final_answer)

Sí. Sin meternos en el análisis de afinación, puedes avanzar bastante en producto/experiencia:

1. **Gestión de canciones**
   - Editar título/artista con modal propio.
   - Agregar portada o color por canción.
   - Buscar, ordenar y filtrar canciones.
   - Mostrar estado: `sin procesar`, `lista`, `con tomas`, `error`.

2. **Gestión de grabaciones**
   - Renombrar tomas.
   - Eliminar tomas con confirmación.
   - Marcar una toma como favorita.
   - Comparar dos tomas del mismo usuario.
   - Exportar una toma: voz sola, voz+pista, o imagen del desempeño.

3. **Reproductor**
   - Barra de progreso interactiva para saltar a un segundo específico.
   - Botones de retroceder/avanzar 5 o 10 segundos.
   - Control de velocidad: `0.75x`, `1x`, `1.25x`.
   - Loop de un segmento para practicar una parte difícil.

4. **Interfaz**
   - Mejorar la vista de biblioteca con tarjetas más limpias.
   - Crear una vista dedicada de “Canción” con historial, botones y detalles.
   - Añadir modo compacto / modo grande para el gráfico.
   - Pulir modo claro/oscuro y dejar temas más consistentes.

5. **Flujo de práctica**
   - Cuenta regresiva antes de grabar.
   - Botón “ensayar sin guardar”.
   - Botón “guardar / descartar toma” al terminar.
   - Notas o comentarios manuales por toma: “fallé en el coro”, “mejor respiración”, etc.

6. **Configuración**
   - Seleccionar micrófono desde la app.
   - Seleccionar salida de audio.
   - Ajustar latencia manualmente desde ajustes.
   - Restaurar configuración por defecto.

7. **Presentación del proyecto**
   - Pantalla “Acerca del proyecto”.
   - Explicar el flujo: agregar canción, practicar, revisar resultado.
   - Mostrar versión, librerías usadas y créditos.
   - Agregar documentación técnica para tu tesis.
